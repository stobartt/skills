# Project context

Read this when establishing a brandbook, redesigning its system, or resolving ambiguous scope. Use the project's existing brief, brand documentation, or equivalent source of truth for established decisions. Record new decisions there when changes are in scope; these prompts do not require a new form, file format, or strategy document.

## Establish the inputs that affect the work

| Concern | Relevant project decisions |
| --- | --- |
| Purpose and identity scope | What is being identified: a product, organization, system, service, event, or another entity? What does the guide need to make recognizable or consistent? Preserve the declared breadth of use. |
| Readers and applications | Who will apply the guide, what will they produce or decide, and in which contexts? Record brand audience distinctions separately when relevant. |
| Existing identity | Locate names, masters, rules, language conventions, and evidence for established choices. Identify what the request preserves and what it asks to change. |
| Deliverables and constraints | Required media, formats, languages, themes, sizes, accessibility conditions, production requirements, and available tools. Choose these from actual uses. |
| Relationships and reuse | Where applicable, identify parent brands, product families, partners, or consuming products, and the rules each relationship imposes. |
| Maintenance | Locate authoritative sources and identify who can resolve or change decisions where known. Use the project's existing versioning and review process. Record material ownership gaps when they affect delivery. |

For an existing identity, document and reconcile its decisions. For a request to develop new foundations, identify the questions that actually need investigation; audience research, competitive context, or positioning may be relevant to that request. Comparative brand guides provide methods and examples, not evidence about this project's customers, market position, or claims.

## Distinguish decision status

| Status | Treatment |
| --- | --- |
| Established | Cite the brief, user instruction, approved asset, or other authoritative project source. An explicitly general-purpose remit is an established scope even when no narrow audience is specified. |
| Proposed | Present a candidate decision with its rationale and tradeoffs. Keep its provisional status visible in examples and delivery claims. |
| Unresolved | Name the missing input or conflict, which decision it affects, and what can proceed independently. Seek clarification only when it materially changes the result. |
| Outside scope | Omit inapplicable work, such as print specifications for a web-only package. Record a brief reason when omission might otherwise look like a gap. |

For a consequential rule, retain its decision, rationale or evidence, applicability, and status together. This can be a short note in the existing guide. A narrow correction does not require classifying every unrelated decision.

Use the current request and project requirements to choose among recommendations from this skill or reference brands. If authoritative inputs conflict and their relationship changes the outcome, expose that conflict before treating a proposal as a settled rule. A dependency affects readiness only for the work that relies on it.

## Adapt shared systems deliberately

For a system used by multiple projects, distinguish its own identity from the identities of products built with it. Document whether downstream projects inherit, customize, replace, or omit particular elements according to the intended reuse model. The fact that a system is general-purpose does not establish a licensing or branding relationship by itself.

Describe the agreed boundaries: fixed rules, configurable defaults, optional elements, and per-project decisions. Show representative adaptations when needed to demonstrate those boundaries. Keep each consuming project's resolved values with that project, linked to the shared rule they implement or extend.

For example, “provide enough clear space to preserve recognition” is a transferable concern; the actual measurement and minimum size belong to the identity being used. A system may supply a default type scale while a consuming product selects fonts under its own language and licensing constraints. Choose such arrangements from the brief rather than making them universal requirements.

The context is sufficient when the agent can select the relevant work, preserve established constraints, and identify the consequences of remaining uncertainty without inventing project facts.
